# Stele — досье решения (для внешней оценки)

*Документ для специалиста: что это, как устроено, что доказано измерениями, где риски и какие
стратегические развилки открыты. Всё честно, включая то, где мы слабы. Числа — из воспроизводимых
прогонов, а не из маркетинга.*

---

## 0. TL;DR (вердикт за минуту)

**Stele** превращает кодовую базу в **навигируемый граф концептов**: код, документация и продуктовые
правила крепятся не друг к другу напрямую, а к общему «спинному хребту» — онтологии предметного языка
(ubiquitous language). Retrieval идёт **онтологией-первой** (резолвим термин → идём по типизированному
подграфу → достаём артефакт), а не плоским vector top-k. Отдаётся агентам через **MCP** и людям через
**CLI/HTTP**. Работает локально (один SQLite-файл, ноль инфраструктуры, локальная LLM по умолчанию).

**Главный измеренный вывод (после независимого ревью и переделок):**
- **Q&A по вопросам поддержки/PM:** граф даёт **3× artifact-recall** против наивного vector RAG при том
  же бюджете токенов, но **качество ответа маленькой модели — паритет** с vector RAG (не превосходство).
- **Rule-compliance кодинг-агента:** вот здесь **структурная победа, которую бесплатный код-граф
  повторить не может** — `структура кода (ast-index) ≤ ничего < Stele+правила`, McNemar **p=0.031**.
  И это подтверждено **живым циклом**: маленькая модель сама вызывает инструмент, тянет правило и
  соблюдает его (3/3 против 0/3 на неочевидных правилах).

**Стратегический вывод ревью (я с ним согласен):** настоящий клин — **не** support-Q&A (там паритет с
дешёвым RAG), а **rule-compliance для кодинг-агентов**. Q&A стоит держать как демо, а питч разворачивать
на «агент не нарушает продуктовые инварианты».

## 1. Идея

AI-агенты хорошо знают, *что* за код (структура, символы, call-граф) — это делают GitNexus, SCIP,
ast-index. Но они не знают, *почему* код такой: **продуктовые правила**, доменный язык, дизайн-интент.
Поэтому агент пишет код, который компилируется и выглядит правильно, но тихо ломает правило —
«завершённый документ нельзя удалять», «токен не должен доставать чужие команды», «после отправки
получателей менять нельзя».

Ставка Stele: сделать **слой концептов (онтологию)** первоклассным и связать через него код ↔ доки ↔
продукт ↔ (в перспективе) Figma. Концепт — это узел-стык: определение + продуктовые правила +
реализующий код + доки + связанные концепты. Кросс-модальная связь — это всегда *путь через концепт*,
поэтому оно язык-агностично (Go + TS + Kotlin + что угодно) и работает на легаси.

**Целевой сценарий (по ревью — уточнён):** сначала думали про support/PM Q&A для маленьких моделей;
ревью показало, что там паритет с RAG, а сильная сторона — **соблюдение правил кодинг-агентом**.

## 2. Как это устроено

### Архитектура (4 слоя + хребет)

```
Источники (коннекторы)  →  Ингест/self-update  →  Артефакты (код/доки/продукт/агент-слой)
                                                          │
                                              КОНЦЕПТ-ХРЕБЕТ (онтология)   ← это IP
                                                          │
                          Retriever (резолв → traverse → drill)  →  Serving (MCP / CLI / HTTP)
```

### Конвейер (одна команда `stele sync` по конфигу `stele.yml`)

```
код → ingest symbols (tree-sitter: декларации → кандидаты-концепты, кластеризация по фиче-папке)
     → build-ontology (LLM канонизирует: имя + определение + bounded context; отсекает инфра-шум)
     → dedupe (детерминированно сливает дубли-близнецы по нормализованному ключу)
     → ingest docs (Markdown → describes-рёбра + ПРАВИЛА как узлы + алиасы + relates)
     → ingest agents (.claude/.agents/CLAUDE.md → отдельный AGENT-слой, без загрязнения онтологии)
     → refine-rules (LLM чистит извлечённые правила)
     → review --accept-above (человек подтверждает / bulk-автоподтверждение сильных рёбер)
     → embed (nomic-вектора карточек концептов и секций доков → семантический резолв)
```

**Принцип:** детерминированно-первое, LLM сверху, человек подтверждает. Подтверждённый набор = задумка
моата (но см. риски — это спорно).

### Retrieval (ключевая механика)

1. **Резолв вопроса → концепт**: точное имя/алиас, затем **семантически** (cosine по сохранённым
   карточкам концептов). 50-way выбор, 90% попадание.
2. **Question-aware drill**: внутри концепта секции доков ранжируются по близости *к вопросу*
   (граф выбирает «район», вектор выбирает «дом»).
3. **Двусторонний контекст**: DOCS SAY (тела секций + правила) + CODE DOES (тела символов по спанам).

### Стек

Kotlin/JVM (JDK 21), Gradle. SQLite (sqlite-jdbc, один файл) + Liquibase-миграции. tree-sitter
(java-tree-sitter, прибитые нативы — ноль C-тулчейна). LLM: Ollama локально по умолчанию, опц. cloud
(Anthropic/DeepSeek/любой OpenAI-совместимый). Эмбеддинги: nomic (или офлайн hashing-floor). MCP —
руками написанный stdio JSON-RPC. Модули: `core`, `extractors`, `connectors`, `resolver`, `mcp`, `cli`,
`eval`.

## 3. Что реально построено (инвентарь возможностей)

| Поверхность | Что делает |
|---|---|
| `stele sync` | весь конвейер по конфигу, turnkey |
| `stele ingest symbols/docs/agents/codegraph/astindex/web` | источники в граф (коннекторы — расширяемый seam) |
| `stele build-ontology / refine-rules / dedupe / review` | канонизация + курирование |
| `stele ask "<вопрос>"` | двусторонний ответ: DOCS SAY / CODE DOES / MISMATCH, с цитатами |
| `stele drift <concept> [--all]` | **проактивный аудит**: правило из доков vs реализация в коде → COMPLIANT/VIOLATION/UNVERIFIABLE |
| `stele concept / search / explain` | навигация по графу из терминала |
| `stele graph` | интерактивный оффлайн-HTML вьюер графа |
| `stele serve [--token]` | HTTP: живой вьюер (`/`) + страница ask (`/ask`) + JSON API (`/api/*`) |
| `stele mcp` | MCP-сервер: `concept_context`, `why_code`, `context_for_code` (blast-radius по `calls`) |
| `stele usage` | телеметрия использования MCP (вызовы, hit-rate, «context served») |
| `stele init` | автонастройка Claude Code (skill + `.mcp.json`) + git-хуки на инкрементальный реиндекс |

Мульти-репо: несколько репозиториев в одном графе (ref-префиксы), проверено на documenso + его SDK.

## 4. Измеренные результаты

Всё на реальном OSS ([Documenso](https://github.com/documenso/documenso), e-signature, TypeScript).
Полный протокол и итерации — в `eval/README.md`, `eval/PROTOCOL.md`, `eval/live-loop-p2.md`.

### Ось 1 — Support Q&A маленькой моделью
30 реальных вопросов из GitHub Discussions; отвечает **llama3.2:3b** (фиксирована), меняется только
retrieval; судья llama3.1:8b, строгая рубрика; **K=3**, ± = 95% CI; эмбеддер nomic для всех.

| рука | concept-hit | artifact-recall | ~токены | answer (K=3) |
|---|---|---|---|---|
| **Stele (семантич. резолв + drill)** | **86.7%** | **87.5%** | 2395 | 3.41 ±0.20 |
| Stele (лексический резолв) | 53.3% | 62.5% | 1950 | 3.08 ±0.25 |
| наивный vector RAG | — | 29.2% | 2412 | 3.54 ±0.17 |
| агентный grep (та же 3B в цикле) | — | 0% | **6601** | **2.80 ±0.18** |

- **Retrieval — решено: 3× recall** vs vector при равных токенах (ответ может *сослаться* на источник
  в 87% vs 29%). Провал vector структурный, не от эмбеддера: усиление nomic (task-префиксы) его не
  сдвинуло — чанк в 50 строк это не тот юнит для концепта, размазанного по докам+коду+правилам.
- **Ответы — статистический ПАРИТЕТ с vector RAG** (парные 11W/14L/4T, sign p=0.69). Честно: на
  одно-доковых «как работает X» сырые чанки отвечают не хуже графа.
- **Агентный grep на маленькой модели — значимо худший при 2.7× цене** (p=0.015 vs граф, p=0.002 vs
  vector). 3B не может позволить себе исследовать репо — курируемый контекст это способ конкурировать.

**Кросс-репо (documenso + его официальный TS SDK, один граф):** stele-sem **75% recall vs vector 50%** —
один вопрос собирает контекст из ДВУХ репозиториев (гайд ядра + README SDK + карта кода SDK), чего
чанки/grep структурно не строят.

### Ось 2 — Rule-compliance кодинг-агента (сильная сторона)

**Инжектированный контекст, 41 trap-задача, 2 репо, детерминированные чекеры, без LLM-судьи:**
```
plain 24%   =   ast-index (структура кода) 24%   <   Stele (концепты+правила) 39%
McNemar ast-index → Stele: b=6, c=0, p = 0.031 (значимо)
```
Структура кода не несёт правил — их несёт концепт-слой. Это то, что бесплатный код-граф структурно не
может.

**Живой цикл (P2) — закрывает главный threat-to-validity:** агент-под-тестом = **Haiku** (маленькая
модель), сам решает вызвать `stele ask`, получает реальный serving-срез, применяет правило.

| задача (правило) | arm A (stele) | arm B (plain) |
|---|---|---|
| удаление завершённого документа | **3/3 соблюдает** | 0/3 |
| смена получателя после отправки | **3/3 соблюдает** | 0/3 |
| владелец видит admins-only док | pass | pass (здравый смысл) |
| истечение получателя | pass | pass |

100% arm-A агентов вызвали инструмент и применили правило. **Ground-truth проверен:** оба правила
реально enforced в исходнике Documenso (`delete-document.ts` → `isDocumentCompleted` soft-delete;
`update-envelope-recipients.ts` → «already interacted» / «already complete»), то есть arm-B — это
настоящий баг, а не выдумка из доков. На неочевидных, team-specific правилах — чистое разделение;
на «здравосмысленных» и plain соблюдает (та же дилюция, что в инжектированном прогоне).

## 5. Независимое ревью и что после него сделано

Провели адверсариальное ревью (7 линз по коду + идее, каждая находка перепроверена отдельным агентом).
Итог: «инженерия сильнее, чем стратегию подтверждают её же данные». По его findings отработаны три
волны (все смёржены):

- **P0 — 5 багов потери данных / тихой деградации** (с тестами): неэкранированный `LIKE` в path-запросах
  (мог **удалить артефакты чужого файла**); немодульные мутации под autoCommit → транзакции; канонизатор
  тихо ронял концепты при несовпадении регистра имени; `isProseRule` пропускал строки кода как «правила»;
  `cosine` молча обрезал по короткому вектору.
- **P1 — харденинг serve + честность + тесты**: XSS (`</script>`-breakout, DOM-XSS) закрыты; **токен-auth**
  (non-loopback bind без токена отказывается стартовать); пул воркеров + соединение-на-запрос (был
  тривиальный DoS на одном потоке); предупреждение, когда активен лексический floor-эмбеддер вместо nomic;
  **end-to-end тест** всего конвейера (главный тестовый пробел был закрыт).
- **P2 — живой agent-loop** (см. выше).

## 6. Честные ограничения и риски (важно для решения «куда дальше»)

1. **Q&A-тезис — паритет, не превосходство.** Против ~200 строк наивного vector RAG по answer-quality —
   ничья. Честный клейм по этой оси — *citation-grounding* (правильные артефакты в контексте 87% vs 29%),
   а не «отвечает лучше».
2. **Моат спорен.** «Человеко-подтверждённые рёбра» — это статус-колонка в локальном SQLite, на практике
   часто bulk-автоподтверждённая. Нет data-flywheel между клиентами. Реальный моат нужно ещё построить:
   либо (a) flywheel с согласия, либо (b) владение слотом MCP-в-Cursor/Claude-Code.
3. **Качество онтологии model-gated.** Локальная 8B даёт заметно худший граф (компаундные имена, мусорные
   концепты). Хороший граф = (организованность репо × сила LLM). Честный ICP уже́, чем звучит: хорошо
   структурированные, rule-rich репо + облачная модель на одноразовом шаге канонизации.
4. **Генерализация не доказана.** Все headline-числа — на **одном репо**; вопросы **выведены из реальных
   GitHub Discussions**, но эталонные ответы и точные формулировки — наши (не verbatim из тредов, что
   вносит selection-bias); N≈29 оценённых; судья 8B (не провалидирован против человека/сильного судьи).
   Нужен второй независимый репо/стек, прежде чем клеймить «язык-агностично».
5b. **ИЗМЕРЕНО (exp1, негативный результат — `eval/exp1-rule-dilution.md`).** Самый дешёвый бейзлайн
   (`cat all_rules.md` в системный промпт) **догоняет** скоуп-доставку: на полном корпусе Documenso
   (159 правил, ~3k токенов) compliance у cat-all = 92% — как у Stele (92%); кривая дилюции ПЛОСКАЯ,
   современная маленькая модель находит нужное правило среди 159 не хуже, чем одно. Механика
   context-injection — не дифференциатор при таком размере корпуса; остаётся токен-эффективность
   (паритет при ~150× меньше токенов) — слабая история. Следствие: вес продукта смещается на то,
   что prompt-stuffing не умеет в принципе, — **drift-на-PR/CI-аудит** и **сам майнинг/поддержание
   корпуса правил** (`cat rules.md` предполагает, что кто-то этот rules.md написал и обновляет —
   ровно это Stele и производит). **Свип exp1b нашёл crossover**: с рандомизированной позицией
   правила cat159 = 83%, cat300 = 58%, cat600–1200 ≈ 50%, а скоуп-доставка константна (92%) —
   **точка пересечения ≈ 200–300 правил = граница ICP**. Ниже неё `cat rules.md` честно достаточно;
   выше — скоуп выигрывает +25–33пп. (Оговорки: N=12/ячейку, синтетические дистракторы, одна модель.)
5c. **Зависимость от существования доков.** Documenso аномально задокументирован; у многих клиентов
   правила в головах/Slack. Смягчения: concierge-кодификация tribal knowledge; **обратный drift**
   (майнинг инвариантов из кода → кандидаты-правила с подтверждением человеком) — расширяет ICP.
5. **Retrieval не всегда достаёт нужное правило.** В P2 2 из 6 кандидатных правил не всплыли на
   естественный вопрос (резолв ушёл не в тот концепт). Цикл помогает только когда правило реально
   серважится — это следующая работа по ретриву.
6. **Figma / дизайн-интент — не построено** (Phase 4). В архитектурных доках это позиционируется как
   дифференциатор, но сегодня это вейпорвар.

## 7. Конкурентное окружение

- **Бесплатные код-графы** (GitNexus, SCIP, ast-index, Sourcegraph): дают структуру кода. Наш же
  собственный замер: структура ≈ ничего по rule-compliance (24% = 24%). Мы их **потребляем**, не строим.
- **Vector RAG / кода-ассистенты** (Cursor, Copilot, Continue): на Q&A мы с ними в паритете; на
  rule-compliance у нас структурное преимущество (правила).
- **Enterprise-поиск/Q&A** (Glean, Dosu, kapa.ai, Unblocked): сильнее на общем Q&A и с интеграциями;
  наш дифференциатор — концепт+правила для агентов, а не человека.
- **Фронтир-агенты с agentic-search**: на маленькой модели agentic значимо дороже и хуже; на фронтир-
  модели с 200k контекста brute-force может задавить — наше преимущество максимально там, где контекст
  дорог (малые модели, много репо).

## 8. Открытые стратегические развилки (вопросы к специалисту)

Здесь мне и нужен внешний взгляд — где приложить следующие усилия:

1. **Позиционирование.** Разворачивать питч полностью на **rule-compliance для кодинг-агентов** (там
   структурная, значимая победа), а Q&A оставить как демо? Или есть аргумент удержать support/PM-Q&A как
   отдельный продукт, несмотря на паритет с RAG?
2. **Моат.** Что делать защищаемым активом: (a) data-flywheel (подтверждённый набор правил улучшает
   канонизацию/типизацию между клиентами) или (b) дистрибуция (owned slot MCP в Cursor/Claude Code)?
   Или третье?
3. **GTM при model-gated качестве.** Раз качество онтологии человеко/модель-зависимо — не пойти ли в
   **concierge/hand-curation** (продаём результат руками), а не self-serve? Кому это продавать —
   platform/DevEx-команды 15–60 человек?
4. **Что доказать следующим экспериментом**, чтобы снять главный риск для инвестора/пилота: генерализация
   на втором репо/языке? Живой `claude -p`+MCP на чистом чекауте с настоящими диффами? Масштаб
   rule-compliance до значимости в живом режиме (сейчас живой цикл — качественный, N=2)?
5. **Стоит ли строить Figma-мост** (заявленный дифференциатор) сейчас, или это преждевременно до сигнала
   с rule-compliance?

## 9. Резюме одним абзацем

Инженерно — зрелый, честно измеренный локальный инструмент с работающим полным циклом (ингест →
онтология → правила → serving через CLI/MCP/HTTP), прошедший адверсариальное ревью и харденинг. Научно —
две независимые оси: на Q&A паритет с дешёвым RAG (не продавать как превосходство), на rule-compliance
структурная и статистически значимая победа над код-графом, подтверждённая живым циклом с ground-truth.
Стратегически — самый сильный, конкурентно-защищённый актив это **«агент не нарушает продуктовые
инварианты»**; главные нерешённые вопросы — моат, ICP/GTM при model-gated качестве и доказательство
генерализации. Именно по этим вопросам и нужен внешний совет.
